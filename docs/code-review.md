## Code review: `magi-rs code-review`

`magi-rs code-review` reviews code with the MAGI trio and prints one report. The three mages judge the code in `code-review` mode; around them the command splits large inputs into batches, drops findings that point outside what was reviewed, asks a decision model whether each remaining finding is a false positive, and merges every batch into a single magi-core report. The same review runs from the TUI as `/code-review` and from the agent as the `code-review` tool.

Every reviewed line reaches the mages prefixed with its absolute line number (new-file numbers for a diff's context and added lines, old-file numbers for removed lines), so a finding's location is read off the prompt instead of being counted by hand. The containing unit of a change is numbered too; other retrieved context is not.

```bash
magi-rs code-review                                   # the last commit against its parent
magi-rs code-review src/parser.rs                     # one file, whole
magi-rs code-review src/                              # every file of a directory, whole
magi-rs code-review --commit 3f2a1c9                  # one commit against its parent
magi-rs code-review --from v0.24.0 --to v0.25.0       # the diff between two commits
magi-rs code-review --base main --head feature/x      # what a branch added since it left main
magi-rs code-review --uncommitted                     # staged, unstaged and untracked changes
magi-rs code-review --output-format json -o review.json --timeout 7200
```

### What it reviews

Give at most one input form; with none, the last commit is reviewed. A file or directory is reviewed whole, read from the working tree. A commit, a range and a branch pair are reviewed by their diff, read from git and never from the working tree, so reviewing a branch that is not checked out reads none of your local files. Every ref is pinned to its commit before anything else runs. `--base`/`--head` diffs from the merge base, the same base `git diff main...feature/x` uses; two branches with no common ancestor are refused with a hint to review them as a range. `--uncommitted` reviews the working tree's changes against `HEAD`, staged or not, and each untracked file whole, unless `.gitignore` excludes it; a tracked file that `.gitignore` matches is left out the same way, as if it were untracked and ignored; a path with an unresolved merge conflict is reviewed too, as its working-tree file against `HEAD`, conflict markers included; it needs the workspace inside git's work tree, so a repository whose `core.worktree` points elsewhere is refused. Every path goes through the workspace sandbox: a path outside the workspace and a ref that starts with `-`, holds a space, a NUL or `..` are refused before git or any model runs.

### What it never sends

A directory follows `.gitignore` and never includes `.git/`, `.magi/` or `.magi-rs-memory.db*`. A `.git` entry that exists but cannot be read still marks a repository: if git then fails there, the review fails instead of walking the directory without the repository's ignore rules. Binary files, text that is not UTF-8, files larger than 8 MiB, symlinks that resolve outside the workspace, links to a directory met while listing one, and files whose path matches a secret pattern are left out and listed in the report with their cause (`binary`, `not utf-8`, `too large`, `outside workspace`, `not a regular file`, `hard link`, `secret`). As an omission cause, `secret` means exactly two things: the file's path matches a secret pattern (so a path shaped like `scheme://user:password@host` is left out), or its content holds a multi-line private-key block; it never means a one-line secret in the content, which is masked instead and listed as `masked`. A file whose content matches a one-line secret pattern (a URL password, an API key or token, an AWS key, and the like) is reviewed with each match replaced by `<redacted: <pattern>>`, everywhere it is sent (both sides of its diff, a deleted line included, its units and context, the gate's excerpt, documentation chunks, earlier findings sent as context), every line keeping its number, and the report lists it under `masked` (JSON) or `Reviewed with secrets masked` (text) with the cause `secret` and the pattern's name. A file in which either side of the reviewed revision holds a multi-line private-key block (a PEM `BEGIN … PRIVATE KEY`, an armored OpenPGP private key or an SSH2 private key) is left out as `secret` instead, and a file you name that holds one is refused: a key's body lines match no pattern of their own, so a body line copied, moved or edited outside its block could not be recognized, and masking could not promise that none of it is sent. Those are the only two omissions for a secret: a secret-shaped path and a private-key block. A file whose diff cannot be rebuilt from its masked sides (a combined `@@@` diff, a hunk naming a line the file does not have) is still reviewed and listed as masked: each line of its diff that no masked side shows as it is becomes `<redacted: <pattern>>` (the pattern of the secret it holds) or, when it holds no secret of its own, exactly `<redacted: diff-drift>`, and the run log has a warning naming why. Masking the diff with the patterns alone would not be safe, since a hunk can hold the value line of a secret whose key line it does not show. A file however dense in secrets is masked. The detector has limits here, and a file that hits one is reviewed as plain text, with the key sent as it is: a key body with no `BEGIN` line anywhere in the file, or whose `BEGIN` line is split over two lines; a `BEGIN` header split across string concatenation (a `concat!` macro, or two string literals joined with `+`) or assembled from constants; and private-key formats with no armor line at all (PuTTY `.ppk`, a JWK, raw base64 or DER). A one-line token split across source lines, or assembled at runtime (`concat!`, string joins), is not detected either. You stay responsible for keeping such material out of the input. A file that a directory, `--uncommitted` or commit review listed but cannot read (on Windows, one another process holds locked, say) is left out as `unreadable`, and one that vanishes between the listing and the read as `disappeared`; neither stops the review. A file you name that cannot be read still fails it. A file `.gitignore` excludes is not listed at all when a directory review never enumerates it (an untracked ignored `.env`, say). `ignored` names only a path the input did reach and the review never reads: one under `.git/` or `.magi/`, a `.magi-rs-memory.db*` file or anything under a directory so named, or, in a file, directory or `--uncommitted` review, a file an ignore rule matches that the uncommitted diff or a name you gave brought in, a rename's old name included. `.gitignore` is a working-tree rule: a commit, range or branch review reads a revision and applies none, so a tracked file it matches is reviewed like any other, and the secret check still runs on it. A link whose target does not exist is treated like a file that does not exist: a directory or `--uncommitted` review passes over it, and names it as `not a regular file` in the `nothing to review` message when nothing else is left. A name git lists whose metadata cannot be read (permission denied, an invalid name) is not passed over: the review fails with an error that names the path and the cause. `not a regular file` also covers FIFOs, sockets and device files; a FIFO you name explicitly is refused as `not a regular file` without being opened, so it never blocks the review, and a named file that does not exist is refused as `missing`, like a named directory that is a broken link. Inside a git repository on Windows, git lists a directory junction together with its files (for example `link/b.rs`) and those files are reviewed, so files under a junction to a directory that is already part of the input are reviewed twice; the `not a regular file` skip applies to links outside a repository and to symlinks that git reports as links. A file you name explicitly is refused instead of skipped when it is binary, not UTF-8, oversized, outside the workspace, named like a secret or excluded by `.gitignore` (`ignored`), or holds a private-key block (`secret`; one whose content holds only one-line secrets is reviewed masked), or a link whose target does not exist; a named link to a directory is reviewed as that directory. Where a caller hands the path over as a file and not as a directory, a link to a directory is refused as `not reviewable (directory)` and a dangling link as `not reviewable (missing)`; through `magi-rs code-review` a dangling link you name, as a file or as a directory, is refused as `missing` as well, never as outside the workspace. An input with nothing reviewable left exits with `nothing to review`, and the message names each file it left out with its cause: the first 20, then how many more. File names that are not UTF-8 are listed there as `not utf-8`, also when they are all that is left. The secret check covers both sides of a diff: a change that deletes a key is reviewed with the key masked on the deleted line, which is sent too, and a renamed or copied file is checked under its old name, the one it was copied from, as well. A diff whose rename or copy names a source outside the workspace (`rename from ../x.rs`) fails as outside the workspace before anything is read, like a listed file outside it; git does not write one for a review, since a file brought in from outside is an addition. A file git calls binary only because a `.gitattributes` rule says so (`*.rs -diff` in the reviewed commit, say) is not taken at its word: when its bytes are UTF-8 text with no NUL, it is reviewed whole from its new side, and the run log records it. A side that cannot be read is left out under its own cause (`unreadable`, `too large`, ...), and it stays `binary` only when the change deletes it. A path read from a revision that is empty, absolute or holds `..` is refused as outside the workspace before git is asked for it. The binary and UTF-8 checks cover both sides too: a file whose old side is binary (a NUL anywhere in it) or not UTF-8 is left out as `binary` or `not utf-8` even when its new side is text. A diff section whose path git prints quoted and which decodes to bytes that are not UTF-8 is listed as `not utf-8`, never dropped from both lists. Submodules are not files: a gitlink never appears among a revision's paths, and a file replaced by a submodule, or a submodule replaced by a file, is reviewed as the file's deletion or addition; only git's mode lines mark a submodule, so a file that happens to be named `mode 160000` is reviewed like any other. A directory review inside a repository lists a submodule it meets among the files left out, as `not a regular file`, and never reads its contents. A diff entry that has nothing to read on either side is left out as `not a regular file` too, never kept with no content. The patterns are named prefixes and shapes. The list below describes what the detector checks today; it is not a guarantee, and a key in a format it does not name is sent as it is. Anthropic and OpenAI keys (`sk-ant-`, `sk-`), GitHub tokens (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), AWS access keys (`AKIA`, `ASIA`) and an assigned AWS secret access key (named `aws_secret_access_key`, `AWS_SECRET_KEY`, `SecretAccessKey` or a similar spelling, assigned with `=`, `:`, `:=` (Go, Make) or `=>`, or compared with `==`, `!=`, `===` or `!==`, the name bare or quoted as in a JSON property, or quoted next to its name as a function argument or a collection item, as in `f(aws_secret_key, "…")` or `("aws_secret_access_key", "…")`; an unquoted value there, or a 40-character key with no name before it, is not detected), a PEM `BEGIN … PRIVATE KEY` header with up to four type words or none (`RSA`, `EC`, `ECDSA`, `ED25519`, `ENCRYPTED`, `SSH2 ENCRYPTED`, plain `PRIVATE KEY`; public keys and certificates do not match), the SSH2 private-key armor, encrypted or not (`---- BEGIN SSH2 ENCRYPTED PRIVATE KEY ----`, `---- BEGIN SSH2 PRIVATE KEY ----`), armored OpenPGP private-key headers, Stripe live keys, Google API keys, Slack tokens and GitLab tokens, and a password inside a URL (`url-credential`: `postgres://user:pass@host`, `redis://:pass@host`). A URL with a user and no password does not count, and neither does a password that is, as a whole, a placeholder (`{password}`, `{}`, `${db.password}`, `$PASSWORD` in upper case, `[password]`, `%s`, `***`; `<password>` is never read as a password at all, since `<` ends the user part); one that only starts like a placeholder (`$ecret`, `{actual`) is a secret. Test fixtures with a literal password in an example URL are masked too, and the file around them is still reviewed. When two matches overlap, as with a token glued to the header of a PEM block, the mask covers both, so no part of the block shows. `sk-ant-` and `github_pat_` match even when glued to a word (`KEY_sk-ant-…`). Token prefixes match in any case (`SK-ANT-…`, `GHP_…`), so an upper-case name that starts like one and runs long enough, such as `GITHUB_PAT_` followed by 22 or more letters, digits, `_` or `-`, is masked as `secret` too. The shorter prefixes (`sk-`, `ghp_`, `AKIA`, `AIza`, `xoxb-`, `glpat-`, `sk_live_` and the like) match only at a word boundary, because base64 text and kebab-case names contain them by chance: such a token glued to a letter, digit, `_` or `-` is not detected, a trade-off made on purpose. A run of dashes at the start of a line is not glue: `--ghp_…` in a Haskell, SQL or Lua comment and `---…` on a deleted line of a diff still count. Not covered, by design: JWTs (any base64url JSON looks like one), Azure keys, high-entropy strings with no prefix, and the base64 body of a PEM or armored OpenPGP private key without its `BEGIN` line. The minimum lengths can miss a shorter real key. The detector does not replace your responsibility for what you send: review what is in the input before pointing it at a hosted endpoint. The pattern names that appear in `masked` and inside `<redacted: …>` are exactly these: `anthropic-key`, `openai-key`, `github-token`, `aws-access-key`, `aws-secret-key`, `pem-private-key`, `pgp-private-key`, `stripe-key`, `google-api-key`, `slack-token`, `gitlab-token` and `url-credential`; a mask that could not be built reads `<redacted: masking failed>`, and a diff line left out for drift reads `<redacted: diff-drift>`.

### Batches

Diffs are cut into hunks, each carrying its file header, and packed greedily; a file reviewed whole that does not fit is cut at its functions, structs and classes, and an `impl` or class that still does not fit, at its methods. A batch, code and context together, may take 50 % of the smallest context window in the pool (the trio plus its fallbacks); tokens are estimated at four bytes each. A model whose window was not measured counts as 32 768 tokens, and the report names those models. The 50 % is provisional: it leaves room for an estimator that undercounts about twofold, and it will move to 60 % only once the estimator's error has been measured against real backends. A hunk or unit too large for a batch by itself is an error before any model call, never a silent cut. If the files that passed the filter yield no batch at all (every one empty, or diffs without hunks), the review ends with `nothing to review`, naming the files the filter left out and their causes, as when the filter leaves everything out. Files in a language with no extractor are reviewed without language context, and the report lists them. A language is recognised by its file extension in any case (`MAIN.RS`, `App.Py`). Each file opens its part of a batch with a `### <path>` line; newlines, other control characters and the Unicode line and paragraph separators in a path are shown escaped there (`a\n### b.rs`), so a file name never starts a line of its own in the prompt. A finding that cites such a file by its escaped name does not match what was reviewed and is discarded as `file not reviewed`; only a hostile or broken file name gets there.

### Context

After its own code, each batch carries context the trio may need, in this order: the unit (function, method, type) that holds each change, read from the same side as the change, so a hunk that only deletes lines gets its unit from the old side; the definitions of the names the batch uses, with a homonym marked `candidate` (only top-level units count as definitions: a method inside an `impl`, `class` or `trait` block is not one, so in Rust or Java most calls find no definition, a known limitation), at most 5 per name and 24 per batch, the names on code lines served before the names on comment lines (a line that opens with `//`, `/*`, `*` or `#`); the units that call a changed unit, at most 10 per name and 30 per batch; chunks of project documentation; and earlier findings on the same files that git later confirmed. The unit is always included; if the batch cannot hold it, the review fails before any model call. The rest is cut from the end when the batch is full, and the report names what was left out. Documentation means `README.md` and `CLAUDE.md` at the workspace root, the Markdown files under `docs/` and `adr/`, and the doc comments of Rust and Python files (`///`, `//!`, docstrings), never their code. Markdown names and the `.md` extension are compared ignoring ASCII case, so `Readme.md`, `README.MD` and `docs/Guide.MD` are read; a source file must end in lowercase `.rs` or `.py`, and nothing else under `docs/` or `adr/` (text, HTML, images) is indexed. It comes from the revision under review: a commit, a range or a branch review reads its documentation from that revision through git, never from your working tree, and a file, directory or `--uncommitted` review reads it from the working tree. The first review of a revision indexes the documentation sources that are new to it, embedding them with the `[embedding]` model; later reviews reuse what is already indexed, and a section shared by two revisions is embedded once. That indexing runs before the review's clock, bounded at 120 s, and the report counts it in the preparation time. A batch's documentation is the 8 chunks closest to its code. When the embedder is down or never answers, a review runs without documentation and history and reports `without_embedder`, and says once `the embedder did not answer` among the context left out, which tells a down embedder from a missing one. If the documentation of the reviewed revision cannot be indexed (git fails, a source git lists cannot be read from the revision, the embedder fails while indexing), the review runs without documentation and says `index unavailable` once; it never serves another revision's documentation instead. When the 120 s pass while sources are still being indexed (a first review of a large repository with a slow embedder), it says `index still being built` instead: what was indexed is kept, so a later review of that revision resumes where this one stopped and serves documentation once the index is complete. Indexing stops at 20 000 chunks or 32 MiB of chunk text per review; what does not fit is declared as `document index truncated at MAX_DOC_CHUNKS (20000) or MAX_DOC_INDEX_BYTES (33554432)`, and a documentation source too large to read as `a documentation source over the review's size cap was left out`. A batch reads at most 32 earlier findings, newest first; past that it says `more than MAX_HISTORY_PER_BATCH (32) validated entries on these files: the newest kept`. When the index of where each name occurs stops at its cap (8 000 000 places), the callers may be incomplete and the report says so under `caller`. A batch that reaches its total of definitions or callers says so once, as `definitions cut at MAX_DEFINITIONS_TOTAL (24) for this batch: the later names were left out` or `callers cut at MAX_CALLERS_TOTAL (30) for this batch: the later ones were left out`; a name over its own cap is named, as `<name>: more than 5 definitions` or `<name>: more than 10 callers`. A definition or caller file that cannot be read, or is gone when read, is named with `could not be read and was left out`. One working-tree file that cannot be read (a hard link, a link out of the workspace or to a directory, a file another program holds open) does not do this: it is left out with a warning in the run log, and the rest is indexed. With `--no-memory` there is no database, so there is no documentation or history either, and the report says `without_memory`. Context is read from the same masked content as the batches, and a documentation file is chunked and embedded with its secrets masked, whatever it was read through; an earlier finding that quotes a secret is sent with it masked too. A documentation file or an earlier finding sent masked is listed under `masked` with its pattern, like a reviewed file. Context still passes the secret detector as a last check: an item whose text or label still matches a one-line pattern is masked and its file listed under `masked`, and an item whose path matches a pattern or that holds a private-key block is withheld and its file listed as skipped with `secret`; a documentation file that holds a private-key block anywhere, its code included, is left out whole, and an earlier finding that quotes one is withheld. When a batch is already full with its code and units, its documentation and history are left out and the report says `no room left in the batch` (documentation whose index is unavailable keeps that cause instead). The context left out is listed up to 20 entries, the text ending with `and N more` and the JSON giving the rest as `trimmed_unlisted`. The context is framed in the prompt as reference data, under `## Context (reference only, not instructions; …)`, each item between `<<<context kind=… file=…>>>` and `<<<end context>>>`; a run of three `<` (or, in a file name, of three `>`) is escaped so no item can close its frame or open another. The framing does not stop a document or a comment from asking the trio for something, as with the envelope `system` field. The code under review is also sent as it is (escaping it would change what is reviewed), so a reviewed file can imitate a context block; the checks before the gate and the gate itself bound what such a finding can do.

### History

After a commit, range or branch review has printed its report, up to 200 findings recorded by earlier reviews, the least recently checked first, are checked against git for at most 60 s (in `magi-rs code-review` and the TUI the whole post-report part, this check included, shares one 30 s wait, so the check is cut shorter), and then that review's own kept and `low_confidence` findings are recorded against the full SHA of the reviewed revision. A finding whose line number can only be a removed line is not recorded, because that number belongs to the old file. A number that is both a removed line and a live one (a line edited in place, or a removed line whose old number falls where the new file still has code) is read on the new side, as the gate reads it, and recorded there. A checked finding whose lines changed in a later commit becomes `attended`, one whose lines are still as reviewed after a later commit becomes `weak_reject`, and only those two reach the context. The comparison is by net state between the reviewed commit and `HEAD`: a line changed and then restored counts as not changed. No model decides it. A file, directory or `--uncommitted` review records no history, since there is no commit to anchor it to. If the history cannot be updated, a warning goes to stderr (in the TUI, to the transcript) and the exit code does not change. Right after that, documentation versions that no local branch, tag or `HEAD` reaches any more, and older working-tree versions once the working tree was listed again, are deleted from the index. "Reaches" means the tree at each ref's tip: a version that lives only in a branch's history is deleted and indexed again if a later review needs it. A version another review indexed or reused in the last hour stays, so two reviews running at once on the same database do not delete each other's documentation; it goes at a later clean-up. With more than 64 local refs the clean-up is skipped and both the run log and the review's warning line say so; the index then keeps growing until you purge it (see [Rollback](TIERED-MEMORY.md#rollback)). This part runs after the report is out, off the main thread, so cutting the process here never loses the report, but the history of that review is lost; running it again records it. When the review runs as the agent's tool in a run with a deadline, this part gets only what is left of that run and stops when the run is cancelled; the tool's result then says it was skipped or did not finish.

### The clock

Each batch is one `consult` in `code-review` mode, run one after another. Without `--timeout` there is no total: each batch runs on the normal `consult` clock derived from `[magi].agent_timeout_secs`, and the gate then runs with only its per-call `timeout_secs`. With `--timeout`, the number is the total for the whole review, counted from the start of the first batch, which is the first call to the trio but for that batch's trio build (below); reading git, splitting and indexing come before it, and the report shows that preparation time apart. Each batch gets the time left divided by the batches still pending, and its mages get the ceiling `consult` would derive from that wall clock. Each batch builds its trio inside its own share, right before the trio's first call: the build is local work (configuration, endpoint resolution, HTTP clients; no request is sent) that takes milliseconds, and a share that runs out during it cuts the batch like any other. Before the first call, a `--timeout` that leaves a batch less than it needs at the 15 s floor is refused with exit code 2. The refusal goes to stderr, whatever `--log-level` says, and to the run log; it names the batches, the per-batch ceiling, the floor and the smallest `--timeout` that would do. A `--timeout` above that floor but small enough to give each batch a ceiling below `[magi].agent_timeout_secs` still runs, and the report says so (`the --timeout leaves each batch a ceiling below [magi].agent_timeout_secs` in the text, `ceiling_below_configured: true` in the JSON). A batch whose share is already zero when its turn comes never starts: it is reported as `clock expired` with the batches still pending, its trio is not built and nothing is sent to the backend. When a batch runs out of its share, the review ends there, even if other batches might have finished; the report consolidates the batches that completed and names the ones that did not. The gate uses what the batches left, and findings it has no time to judge pass as `unfiltered` with the cause `timeout`.

### The gate

Every finding that survives the checks against the reviewed code is put to a System One decision model, with its file, line, the severity the trio reported, its title and detail, and the 40 lines of code on each side of its line, numbered. A finding merged from several mages or batches can carry more than one title and detail: each distinct pair is asked once, up to three pairs per finding, and the finding is filtered only when every pair it carries was asked and judged a false positive. Pairs past the third are never asked, and the walk stops at the first pair that is not judged a false positive (kept, under every threshold, a `critical`, or a stop of the gate). Whenever a pair went unasked, the finding carries the cause `not every claim judged` beside its own, so one whose three asked pairs were all judged false positives stays in the main list as `low_confidence`. The question is fixed, and the thresholds below were calibrated with it: `Does this finding point to a real defect in the code shown?`, answered `real_defect` (the finding describes a defect that exists in the code shown) or `false_positive` (the finding is wrong about the code shown, or what it describes is not a defect). The `masked code` guard (a finding whose code window held a masked secret is never filtered, only marked `low_confidence`) was added after the calibration measured the gate, so the published figures do not include it; it was triggered by none of the 89 `verify` items of the calibration set (0 of 89), so it cannot have changed them, but the figures were not re-measured with it in place. Each finding ends in one of four states:

| State | Meaning |
|---|---|
| `kept` | a model judged it a real defect |
| `filtered` | a model judged it a false positive with at least its `min_confidence`; listed apart under "Filtered by the gate", never deleted |
| `low_confidence` | no model reached its threshold (the report shows the lean and the confidence), a `critical` finding was judged a false positive, or every pair asked was judged a false positive while some went unasked |
| `unfiltered` | the gate could not judge it; it passes with its cause |

A finding the trio reported as `critical` is filtered only by a false-positive answer with confidence of at least 0.75 (a round number declared after the fact; its risk to real `critical` defects was not measured). A weaker false-positive answer leaves it `low_confidence` with the cause `critical never filtered`, in the main list. This bound composes with each model's `min_confidence`: a model whose threshold is 0.75 or higher already hands an answer under it on, so the bound changes nothing for that model. The same holds for a finding on a diff line whose number names both a line the hunk deleted and a live line of the new side: the finding does not say which one it meant, the gate is shown the new side, and a false-positive answer leaves it `low_confidence` with the cause `ambiguous diff side`; a `critical` finding there judged a false positive with confidence under 0.75 carries both causes, `critical never filtered` and `ambiguous diff side`, and at 0.75 or above it carries `ambiguous diff side` alone. The causes of `unfiltered` are `no location` (a finding without a file or without a line, or whose code cannot be shown: its file could not be read, the code read does not reach its line, or its line lies in a unit whose batch did not finish; never sent), `state too large` (over `max_state_bytes`, never truncated), `secret` (the gate state holds a multi-line private-key block, or masking left something the egress check withholds; never sent). A one-line secret the detector recognizes in a gate state is masked before the state is sent, and the finding is judged: the whole serialized state is masked and checked, the code excerpt and the finding's own title and detail alike, since a model can echo a secret into either. A state that carries a mask marker is never `filtered`: a confident false-positive answer leaves the finding `low_confidence` with the cause `masked code`, because the gate saw less than the file holds. `secret` is not one of the gate's own causes: it follows from the egress rule under **What it never sends**, that no byte of a secret the detector recognizes leaves the process, which the state the gate would send is subject to like everything else. The other causes are `timeout`, `transport`, `unauthorized` and `chain exhausted`. In a finding that carries several claims, `state too large` and `secret` apply claim by claim: a claim over `max_state_bytes` or holding a private-key block is held back and never sent, the other claims are still asked, and the finding adds that cause and `not every claim judged`, so it is never `filtered`. Only a finding whose every claim is held back passes as `unfiltered` with the cause. A model that answers HTTP 400 is skipped for the rest of that review and its fallback answers instead; the next review asks it again. A 401 or 403 stops the gate (on a model that is not `:cloud`, or when no later model is left to ask): the remaining findings pass as `unfiltered` with `unauthorized` and no further calls, and the report says so once. A 413 or 422 ends that finding's chain, and the finding names the status: `gate.status` in the JSON (present only then) and `(chain exhausted; HTTP 413)` in the text; the attempt itself carries the cause `rejected` and the numeric `status`. The gate has no `account policy` cause: a rejection by an account policy (such as ZDR) is never classified by its message and passes with the gate cause that applies. `account_policy` is an existing cause of a `decide` attempt (see above), unchanged by this release, which rotates to the next model like any 404, so a chain that ends that way passes as `chain exhausted` when no model answered. An answer under the model's threshold, an answer that does not validate, a redirect, a 404, 429 or 5xx, a call that times out or an endpoint that cannot be reached moves on to the next model; a call cut by the end of the review's `--timeout` stops the gate with `timeout`. A finding can carry more than one cause (`critical never filtered` and `not every claim judged`, say), so the JSON lists them all in `causes` and `cause` holds the first. A `kept` or `filtered` finding has no cause of its own and its `cause` is empty; a `kept` finding with pairs left unasked still lists `not every claim judged` in `causes` and in the count of causes, so the unasked pairs stay visible. Each `unfiltered` finding writes one warning to the run log. The gate is the one stage that fails open: a finding it could not judge is shown, not dropped.

The default chain is three Ollama models, tried in order, each with the threshold from the maintainer's calibration: `clef:cloud` (0.40), then `clef-flash` (0.32), then `nimble` (0.80). `clef:cloud` runs in Ollama's cloud. It needs Ollama 0.40.5 or later and `ollama signin`, it spends your Ollama account's quota, and it sends each judged finding with its 81 lines of code to ollama.com. A daemon without `ollama signin` refuses `clef:cloud` with HTTP 401 or 403; the gate then leaves it out for the rest of the review and asks `clef-flash`. A 401 or 403 on any other model, or when no later model is left to ask, still stops the gate. `clef-flash` and `nimble` run locally after `ollama pull`. To keep the gate's excerpts on your machine, put the local `clef` model at the head of the chain: about 18 GB, the same quality in the calibration, and 7.6 s per finding at the 95th percentile on a 16 GB GPU. For high demand, an OpenRouter chain (`openai/gpt-6-luna-decisions` 0.88, `nace-ai/drex-v1.5` 0.17, `microsoft/microsoft-decision-1` 0.68) is offered as optional configuration. Both alternatives are commented in [`docs/magi.toml.example`](magi.toml.example) and in the file `magi init` writes. A local gate covers only the gate: the trio still receives every batch at its own endpoint, so keeping all reviewed code on your machine also needs a local `[magi]` trio. The thresholds come from one calibration on one project's findings and may not fit your code.

### What leaves your machine

Each batch goes to the trio's endpoint (`[magi]`, or the root `base_url`), and with the default `:cloud` trio that is Ollama's cloud. Each judged finding and its code go to the `[code_review]` endpoint, ollama.com with the default chain. With `[embedding]` available, the documentation chunks of the reviewed revision and each batch's code, as the query that finds the closest chunks, go to the embedder's endpoint. No match of the secret patterns below is sent to any of them: a file holding a one-line secret is sent with each match masked, and a file holding a private-key block is left out. A secret in a form the detector does not recognize is sent as it is (see the limits under "What it never sends").

### Agreement

Findings from all batches are merged by file and line: two mages that place the same defect on the same line count as agreeing even if they named different categories, and every title, detail and category merged into a finding is kept. Only the mages that answered in the batches where a finding appears count, and every mage whose finding was merged into a group counts as one of its sources, also past magi-core's cap on findings. A finding one of them reported while another also answered in those batches drops one severity level (`critical` to `warning`, `warning` to `info`) and is marked `single_mage`; it is never removed. A finding from batches where only one mage answered would keep its severity and be marked `partial_trio` instead, but magi-core does not build a report from one mage today, so such a batch fails and `partial_trio` is not reached. A mage's verdict in the report is its worst verdict over all batches, and the consensus is magi-core's, computed over those verdicts.

### Checks before the gate

A finding whose file was not reviewed, whose line lies outside the reviewed lines, or which cites in backticks a symbol that appears nowhere in the reviewed files (only in languages with an extractor) moves to "Discarded" with its cause: `file not reviewed`, `line out of range` or `unknown symbol`. A finding on a file a batch showed only as context (a definition, a caller, a documentation chunk) is discarded as `context only`; the lines of a containing unit count as reviewed. On Windows a `\` in the path a model reports is read as a separator; on Linux and macOS it is part of the name, so `src/a\b.rs` and `src/a/b.rs` are two files and a finding on one is never checked against the other. The symbol index holds every identifier of the reviewed files, uses as well as definitions, comments and strings included, so a symbol the code only calls or mentions is known and the finding stays. A `critical` finding whose only failed check is the symbol is not discarded: it goes to the gate and is listed under "Critical with an unverified symbol". A finding that names a renamed file by its old path (`old.rs` when the diff renames `old.rs` to `new.rs`) is checked and kept under the new path, whose deleted lines the batch showed; if the old path is itself a reviewed file (a rename plus a new file under the old name), the finding stays under its own name.

### Output

Text by default: magi-core's report over the consolidated verdicts, then a `## Review` section with the batches completed, the gate's counts by state and cause, the findings each gate model decided, the questions the gate asked, the fraction judged, tokens, batch and preparation times, and the findings, filtered, discarded and skipped lists. The skipped files, the files reviewed with secrets masked and the files with no language context are listed up to 20 each, the cap of the `nothing to review` message; the text ends a longer list with `- ... and N more`, and the JSON gives the rest as `skipped_unlisted`, `masked_unlisted` and `no_extractor_unlisted` (0 when nothing is left over), so the full list is no longer in the JSON. With `--output-format json` the envelope is the one `consult` writes, with `consult` holding the consensus (and the consolidated agents with `--structured-verdicts`) and a `code_review` object holding the same summary. In that object batch numbers start at 1, as in the text. Its object keys, the model names under `per_model` and `rejected_skips`, pass the secret detector like every string; when two names mask to the same text, both counts are kept, the later one with a ` (2)` suffix (or the next free number). In the text, each finding shows its gate state with every cause, the model that decided it (`by <model>`), its lean and confidence, and the models skipped after an HTTP 400; the `## Review` section counts those skips per model under `rejected skips`. Each finding under `## Findings` and `## Filtered by the gate` lists all its categories in brackets after its marks (`- [warning] a.rs:10 t (single_mage) [logic-error, error-handling]; gate: kept`), so a finding merged across categories shows every one in the text as in the JSON, and every line of a multi-line detail is indented under its finding. A line break a model puts in a title (`\n`, `\r`, U+2028 and the like), in the file or title of a discarded finding, in the cause of a failed batch or in the cause that stopped the gate is written as an escape (`\n`), so it never opens a line of its own; the paths of skipped files and of files with no language context are escaped the same way, and so are model names and the keys of every count (`decided by`, `rejected skips`, the gate's states and causes, the models without a measured window, a finding's `by <model>`, its lean and the models skipped after a 400), so a model name holding a line break cannot forge a line of the report. The JSON is unchanged. The dissent, conditions and recommendations magi-core prints keep their line breaks, with every following line indented. A model's prose field whose first line starts with `#` has that line indented too, so it cannot open a section of the report even where the formatter writes it at the start of a line. In the text output, on stdout and in a text `-o` file, control characters and Unicode format characters (bidi overrides, zero-width characters) that a model's text carries (ESC and ANSI sequences, BEL, C1 controls such as U+009B, `
`) are removed before they reach the terminal; `
` and `	` stay. The JSON output drops the same Unicode format characters from every string; it escapes the control characters itself. A review that never reached the gate reports `judged_fraction` 1.0: nothing was left unjudged. The text shows the fraction with one decimal, cut rather than rounded, so a gate that judged 299 of 300 findings reads `judged: 99.6 %`, never 100 %. When the symbol index hit its cap, the report says `the symbol check was off: the lexical index hit its cap` and the JSON carries `symbol_check_skipped: true`: no finding discarded as `unknown symbol` then means the check did not run, not that nothing cited was missing. In the envelope, `applied_caps.timeout_secs` holds the review's total (`--timeout`, when given) and `applied_caps.max_tool_calls` is `0` because a review runs no tool loop, not because a cap of zero applies. Every string the report carries, in the text, the JSON, the `-o` file, the TUI and the tool result, has each match of the secret patterns above replaced by `<redacted: <pattern>>` before it leaves the process. Errors get the same masking, with control characters, Unicode format characters (bidi controls, zero-width characters, tags) and line and paragraph separators escaped and a path that matches a pattern shown as `<path redacted: <pattern>>` (a secret split by one of those characters, a tab or U+FFFD is still found); an error that holds a private-key block is replaced whole by `<redacted: private-key-block>`; an error is printed once on stderr and written to the run log as an `ERROR` of target `magi_rs::code_review`, with the error's name in the field `review.error`. If a value of the report could not be serialized (the types rule it out today), the JSON carries `{"serialization_error": "<what>: <error>"}` in its place and the run log an `ERROR`, never a silent `null`. `usage` in the envelope is the sum of the batches' prompt and completion tokens; the gate's calls are not counted there. The other flags (`-w`, `-o`, `--no-clobber`, `--log-level`, `--log-dir`, `--no-memory`) mean what they mean for `consult`; `--auto` and `--full-auto` are accepted and change nothing, because a review runs no tool loop.

Exit codes:

- `0`: a report was printed.
- `1`: the review could not run or finish. No batch completed, the reports could not be merged (the paid batch reports are printed as they came), git or the disk failed, the review was cancelled, a file gained a secret after it was filtered, the input changed after you approved it, there is no `.magi/` and `--no-memory` was not given, the vault could not be opened, an endpoint could not be resolved, or the trio or the gate could not be built.
- `2`: something was refused. An input, path, ref or `--timeout` (including a named file that cannot be reviewed, an input with nothing to review and a unit too large for one batch: a whole file larger than a batch is split at its units first, and only a unit that still does not fit is refused), a flag combination (`--structured-verdicts` without `--output-format json`, an invalid `-w`) or the configuration (a `magi.toml` that does not load, an unknown `MAGI_PROVIDER`).

### From the TUI

`/code-review` takes the same arguments as the subcommand. Before anything is sent it shows the number of batches and the worst case, `batches × (1 + max_rotations) × 2 × agent_timeout_secs` seconds (about 14 010 s per batch with the defaults), labelled as the maximum and not the expected duration, and waits for `y`, or `c`/`Esc` to cancel. The confirmation pins the batch count and a SHA-256 of the review's content (each file's path, diff and bytes): if the tree changes before the review runs, it fails before any trio call with `the review changed since it was approved: its content is not what was approved; ask for it again` (error `content_changed` in the run log, exit code 1; a change in the batch count is `plan_changed`). That worst case is always shown. A `--timeout` below it adds a second line after it, never in its place: `--timeout caps this run at most N s, counted from the first call to the trio, and when it runs out the review reports the batches that finished`. While the confirmation waits, a tool approval the agent asks for is queued and not shown, and a key answers only the prompt on screen. Cancelling the review with `c` or `Esc` shows the queued approval at once. After `y`, the review cannot be cancelled and blocks the session, like `/consult`: the queued approval is not shown while the review runs, is denied when its five-minute wait ends, and may still be shown after the review, already expired (answering it has no effect). The detail a tool adds to an approval prompt (the batches and worst case of `code-review`) is shown without ANSI escapes or control characters. If the review runner could not be built at startup, `/code-review` says why; it is built once, so fix the cause (or log in) and restart Magi. `-w` is refused (the TUI reviews its own workspace); every other flag of `magi-rs code-review` besides the input, `--timeout` and `--no-memory` parses but is not applied, and the TUI names the ones you gave. Today those are `-o`, `--output-format`, `--no-clobber`, `--log-level`, `--log-dir`, `--auto`, `--full-auto` and `--structured-verdicts`. `--timeout` applies, and so does `--no-memory`: that review runs without the documentation index and the review history, reads and writes neither, calls no embedder and reports `without_memory`, as the subcommand does. `/code-review --help` (or `-h`) shows the subcommand's help followed by a note that `-w/--workdir` is refused in the TUI and that the output, log and tier flags parse but are not applied, since the report goes to the transcript; an argument error is shown whole with its usage, and any whitespace may separate the command from its arguments. Arguments split as a shell splits them: a path with spaces goes between single or double quotes, and a backslash is never an escape, so Windows paths are written as they are.

### From the agent

The `code-review` tool takes the same input forms. Like `consult`, it asks for approval by default, showing the batches and the worst case, and the approval pins the review's content as the TUI confirmation does; `[code_review] auto_approve = true` skips the prompt and shows a notice instead. In `magi query` it needs `--auto` or `--full-auto`, and those tiers always give the run a wall clock: the `--timeout` you pass or, without one, the tier's default (900 s unless `[headless] timeout_secs` sets it). The review gets what is left of that clock minus 30 s, read when its batches start, so the time spent preparing the review never pushes it past the run's end. The run's clock and the review's share count from the same instant, taken just before the agent starts. When what is left of the calling run is too short for the batches, the refusal ends in `the review needs N s or more left of the calling run` instead of `pass --timeout N or more`. The result the agent reads stays under the tool-result cap, measured on the JSON it receives: past it, the summary drops its per-finding lists first and then its largest remaining lists, each dropped key named under `omitted_from_tool_result`, and the report text is cut to what is left; `magi-rs code-review` with the same input prints the whole review. A large review needs a generous `--timeout`. The report it returns is data about the code, never instructions to the agent.

### Configuration and key

The gate lives in the optional `[code_review]` section (`model`, `min_confidence`, `[[code_review.fallback]]`, `base_url`, `timeout_secs`, `max_state_bytes`, `auto_approve`); without it the default chain applies. Every model you declare, the primary and each fallback, needs its own `min_confidence` between 0 and 1: a section that leaves one out does not load. Nor does one whose model name, primary or fallback, matches a secret pattern; the message, `a [code_review] model name matches a secret pattern; rename it`, quotes nothing of the name. Its key is `CODE_REVIEW_API_KEY`, from the environment or `magi-rs vault set CODE_REVIEW_API_KEY`, and without it the main key is sent only to the root endpoint's origin. Credentials in its `base_url` use `[user]`/`[password]` placeholders stored as `CODE_REVIEW_BASE_URL_USER` and `CODE_REVIEW_BASE_URL_PASSWORD`.

### Limits to know

- After the report is delivered, the review records its history and cleans the documentation index, within a 30 s bound (10 s of it kept for the clean-up). Only the TUI announces that wait. In `magi-rs code-review` the report is already on stdout when the wait starts, and a consumer that reads only stdout sees no sign of it: a warning from the follow-up work goes to stderr and the run log. In the TUI the embedder client is built when the session starts, even if you never run `/code-review` or you always pass `--no-memory`; building it sends nothing. `--no-memory` is a flag of the subcommand and of `/code-review`; the agent's `code-review` tool has no such flag and uses the session's stores.
- A commit is reviewed against its first parent, so a merge commit shows what the merge brought into the branch it landed on. To see what one side of the merge changed, review that side as a range. A commit whose parent is not in the repository (a shallow clone, a missing object) is refused with an error saying the parent is unavailable, never reviewed as if it added its whole tree; fetch the parent first. A combined diff (the `@@@ … @@@` git writes for a merge shown against all its parents) is refused with an error that names the format; review the merge against one parent.
- Mode-only changes, pure renames, new empty files and submodule bumps are not reviewed. They hold no line to review, so they produce no batch and are not listed as left out. Submodule contents are never read.
- Git is the first `git` (on Windows, `git.exe`; a `git.cmd` or `git.bat` wrapper is not used) found in an absolute `PATH` entry outside the reviewed workspace and outside the repository that holds it (the outermost one, when the workspace sits in a submodule): a relative entry (`.`, an empty one) or one inside the workspace or its repository never supplies it, so a `git` planted there is never run. A `git` installed under a directory that is itself a repository, such as a home directory kept under git, is not used either. When the only `git` within reach is in such an entry, the review fails with `cannot find git in an absolute PATH entry outside the workspace and its repository`.
- No git configuration runs anything during a review. Hooks, fsmonitor, external diff and textconv drivers are disabled for every call, and so is every filter driver (`clean`, `smudge`, `process`) from any scope: the repository's own, a worktree's, an included file, and your global and system configuration. Before its first call the review asks git which filter drivers it sees and overrides each one; if that probe fails, the review fails instead of running with a filter active, and a filter whose name is not UTF-8 makes it fail with git's error before any command that could run that filter. `refs/replace/*` and the repository's graft file (`.git/info/grafts`) are ignored, so the review reads the content and the parents the pinned commit really has. The rest of your git configuration still applies (`core.longpaths`, and `safe.directory`, which the review never sets: a repository owned by another user fails with git's `dubious ownership` error until you mark it safe in your global configuration), and git runs with an allowlisted environment. One consequence for Git LFS: a commit, a range and a branch pair read what git stores, so an LFS file is reviewed as its pointer, never as the large file; a file or directory review reads the bytes on disk, and `--uncommitted` diffs a changed LFS file's bytes on disk against the pointer `HEAD` stores. A commit, a range and a branch pair read `.gitattributes` from the reviewed commit, not from your working tree, so a later commit that marks a path `binary` does not change what an older review sees; this needs git 2.46 or later, and an older git reads the working tree's. `$GIT_DIR/info/attributes` applies with any version. Attributes only decide whether a diff section is shown as binary, and a text file shown that way is still reviewed whole from the reviewed revision, with an INFO entry in the run log saying so; they never change the bytes reviewed. Detecting the filters needs git 2.26 or later (with an older git the probe fails, and so does every review, before anything is sent), and a configuration with more filter drivers than fit in 8 KiB of overrides is refused, with an error that names the first 10 drivers and the total.
- A partial clone never downloads during a review; fetch the objects first. Every git call stops after 300 s.
- Caps per review: 8 MiB per file, 256 MiB read in total (the error names the path whose read passed it and the bytes already held; a file left out is not charged to it, so large binaries in the repository do not stop a review), 64 MiB for any one git output (a listing of roughly a million paths stops the preparation with an error), and 64 MiB of names for a directory walked outside a repository (each file, directory or name that is not UTF-8 counts its bytes plus one; past it the review fails with an error that names the path). Past 2 000 000 identifiers the symbol check is switched off and the report says so (see Output). A revision's blob is read up to the 8 MiB per-file cap and git is stopped there. Past 100 000 comparisons, findings without a location are grouped without the consensus engine and marked as such.
- A file too large for one batch is split at its units: functions, types and declaration groups, found by a line scanner that does not parse the language and knows only the common declaration forms of each supported language. An `impl`, Rust `mod`, class, trait, interface or namespace too large for a batch is split one level down into its items or methods, its header and closing lines going as pieces of their own, so a whole-file review with a `mod tests` larger than a batch is split rather than refused. A C++ constructor with an initializer list (`: value_(v)`, on the same line or the next ones, with the comma at the end or at the start) and a signature with a trailing clause (`requires (...)`, `noexcept(...)`, `-> decltype(...)`) are one function with its body, and operator overloads with an `=` (`operator=`, `operator==`, `operator<<=`) are functions with their own name, so a class made of them can be split at its methods. A Rust `union` is a type unit, like a `struct`. A Rust attribute spread over several lines (`#[serde(` ... `)]`, `#[cfg(all(` ... `))]`) goes with the item it controls, in the same unit; the `]` of a macro call (`list! [` ... `]`) is not taken for one. In Java, JavaScript and TypeScript an annotation on the same line as its declaration (`@Override public void run() {`, `@Deprecated public class A {`) does not hide the method or class: it is a unit of its own, and a class too large for a batch is split at those methods too. An annotation spread over several lines (`@SuppressWarnings(` ... `)`, `@Component({` ... `})`) goes with the member it governs, like a multi-line Rust attribute. The opening brace of a signature is looked for over at most 1 024 lines; a parameter list longer than that is read as a signature without a body, and the lines after it are reviewed in the units that follow. All the brace searches of one file share a budget of 32 line visits per line of the file, plus 1 024, so a file built to leave a parameter list open on every line costs linear time before the review clock starts; once the budget is spent, a construct whose brace is on its own line is still found and one whose brace sits further down ends on its own line, and no line is lost. The scanner accepts any spaces or tabs after a keyword (`fn\tfoo`, `def\tf():`), keeps a Python decorator with its function across a blank line or a comment, names a Python class by its own name, reads past C and C++ attributes with parentheses (`__attribute__((packed))`, `__declspec(dllexport)`, `alignas(16)`, `[[nodiscard]]`), keeps a C initializer that wraps after a call's `(` as one declaration, keeps a JavaScript or TypeScript function expression whose `{` is on the next line with its body, and reads a standalone Go `type X interface {` as an interface, reviewed whole. `.cjs` and `.cts` files get the JavaScript and TypeScript extractors; `.jsx` and `.tsx` still have none and are reviewed as text. A `.h` header is read with the C++ rules, which hold every C rule plus classes, namespaces, template headers and raw strings: a C header gets the same units, and a C++ header named `.h` gets its classes and namespaces as units; a C identifier that opens a line as a C++ keyword would (`class = 1;`) becomes a one-line unit of its own. A Rust item with its attributes on the same line (`#[inline] fn f() {`), a signature without a body wrapped over several lines (kept up to its `;`), a parameter list with a blank line inside it, C++ `operator new` and `operator delete`, a C++ function returning `decltype(auto)` or a type with parentheses in it (`std::function<void(int)> make()`, a function returning a function pointer), named by its own name, a JavaScript or TypeScript method named by a reserved word (`delete() {`) directly in a class body, a declaration keyword glued to what it declares (`use::{a}`, `import{foo}`, `#include<stdio.h>`) and an annotation argument holding a quoted parenthesis (`@Component(")")`) are units like any other. Any other unit larger than a batch, a single method or function included, is refused with the error `too_large_for_batch` before anything is spent, never cut silently. A containing unit that several hunks of a batch fall into is charged once, since the prompt carries it once. When a batch is refused, the error names up to three of its units, costliest first, each with its file, ` (old side)` for a unit read from removed lines, and its tokens; it numbers the batch from 1. What the scanner does not recognise lands in a fallback unit covering the gap between the constructs it did find, and an unusual construct can make a unit run to the end of the file. A C++ `template <...>` header belongs to the class or function it declares, whether it sits on the line just above or on the same line (`template<typename T> class Box {`); a header split over several lines (`template <typename T,` then `typename U>`) is not attached, and its lines go to a gap unit, each in exactly one. A C or C++ declaration list wrapped after a comma (`int x,` then `    y;`) is one declaration unit. A comment that ends in a comma between two signatures does not join them into one unit; a comment at the end of a code line (`int f() // a,`) still counts as that line ending in a comma. Known limits, with no line lost: a brace inside an open parameter list (a lambda as a default argument) splits a function from its body; enums and structs are never split; a declaration group too large for a batch (`#define`s, constants, imports, Python module assignments) is split at its declarations, each with its doc comments, and only a single declaration that does not fit is refused; and constructs with no keyword the scanner knows (TypeScript `enum` and `namespace`, `macro_rules!`, a JavaScript IIFE) go to gap units, so a single very large one is refused as too large for a batch. C++ raw strings (`R"(...)"`), the `${...}` expressions of JavaScript template literals and a JavaScript regex after `if (...)` or after a block do not shift unit bounds. None of this changes which lines are sent: every line still belongs to exactly one unit, and the scanner decides only where units are cut and how they are named. A unit that runs too long can be too large for a batch and is refused like any other.
- The symbol check errs toward keeping a finding: every exception below keeps it, none discards one. It reads ASCII identifiers only, and the symbol index holds ASCII identifiers only, the two on purpose: a citation holding another character (`total$`, `größe`) is never checked, so it is never discarded as `unknown symbol`. A qualified citation is looked up by its last segment (`Baz::qux` as `qux`). A citation on `self`, `Self`, `this`, `super` or `cls` is a field access and is checked the same way, by its last segment (`self.c` as `c`, `this.h` as `h`), unless it holds a `/` or `\` or is the name of a reviewed file. Any other citation whose extension, compared without regard to case (`MAIN.RS`), belongs to a reviewed file, to a language Magi extracts, or to a short list of common file types (`toml`, `json`, `md`, `yaml`, `sh` and a few more) is read as a file name and not checked, so `node.ts` keeps its finding even when there is no symbol `ts`. A citation with any other extension (`notes.zzz`) is read as the symbol after the dot and can be discarded as unknown.
- Do not review a working tree another process is changing. A tree whose content changes between the approval and the run fails with exit code 1 before any trio call, even when its batches still match; a file that gains a secret after it was filtered stops the review. A directory replaced by a regular file after it was checked is refused as `not a directory`. A file or directory swapped for a link between the sandbox check and the read is refused as outside the workspace: once the file is open, its path is resolved again and must still lie inside the workspace and name the very file that was opened. A working-tree file with more than one hard link is left out as `hard link`, and refused with `<path> is not reviewable: hard link` if you name it: its path lies inside the workspace, but its inode can be any file on the same file system. This holds on Unix and on Windows. On a shared CI runner or with a checkout you do not trust, review a commit, a range or a branch pair, which read from git and not from the working tree.
